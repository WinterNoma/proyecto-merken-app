# Pulsys — Qué frontend permite escribir e iterar más rápido

**Corte y fecha de consulta de todas las fuentes: 18-11-2026.** Las fechas adicionales indican una publicación o versión identificada. El análisis separa las capacidades documentadas de las estimaciones para Pulsys. Es una revisión documental, sin builds ni pruebas físicas. El [informe anterior](alternativas-tauri.md) ya compara arquitectura, requisitos de distribución, compatibilidad de dispositivos, voz, SLM y migración del núcleo.

## Recomendación

**Si la prioridad es ahorrar tiempo escribiendo la UI, empezaría por Svelte 5 + TypeScript en el Tauri actual.** Probaría un solo flujo con el CSS, el adaptador de datos y la geometría corporal existentes. Svelte permite expresar en una plantilla lo que hoy se construye y sincroniza mediante llamadas al DOM. Mantendría inicialmente la gráfica SVG y las interacciones actuales para que la comparación aísle el efecto del framework. La expectativa de menos código y menos correcciones es una hipótesis que debe pasar el piloto. [UI actual de telemetría](../ui/src/ui/telemetry-history.ts), [mapa corporal](../ui/src/ui/body-map.ts), [dependencias y scripts](../package.json), [guía de Svelte 5](https://svelte.dev/docs/svelte/v5-migration-guide), [configuración frontend de Tauri](https://v2.tauri.app/start/frontend/).

**Mediría después Compose en Android con una réplica temprana en SwiftUI y, como tercer candidato, Flutter.** Compose y SwiftUI son la referencia para estimar el coste real de dos UIs y sus ventajas para formularios, controles de plataforma y accesibilidad. Flutter permite medir si una UI compartida y el hot reload en el teléfono compensan reescribir el diseño y tender el puente a Rust. Si escribir la presentación en Rust se convierte en un requisito, cambiaría el tercer piloto por **Slint** para evaluar una UI con renderer propio. Para una UI en Rust que conserve el modelo HTML/CSS, el candidato directo es **Dioxus 0.7 WebView**. [Previews de Compose](https://developer.android.com/develop/ui/compose/tooling/previews), [Previews de SwiftUI](https://developer.apple.com/documentation/swiftui/previews-in-xcode), [hot reload de Flutter](https://docs.flutter.dev/tools/hot-reload), [Slint 1.19, 16-11-2026](https://slint.dev/blog/slint-1.19-released), [Dioxus móvil](https://dioxuslabs.com/learn/0.7/guides/platforms/mobile/).

## Qué opción reduce trabajo de UI

Las cuatro opciones TypeScript tienen plantilla Tauri. Con el servidor de Vite y un adaptador de datos falsos, permiten iterar en navegador sobre el layout real. Los cambios de dependencias, arranque o puente pueden requerir reiniciar o reconstruir. Vite transforma TypeScript para servir la UI y la comprobación de tipos se ejecuta por separado. Pasar del navegador al APK es una medición propia. [Plantillas Tauri](https://v2.tauri.app/start/create-project/), [HMR y TypeScript en Vite](https://vite.dev/guide/features.html).

[Previews](https://developer.apple.com/documentation/swiftui/previews-in-xcode), [contentShape](https://developer.apple.com/documentation/swiftui/view/contentshape%28_%3Aeofill%3A%29), [LineMark](https://developer.apple.com/documentation/charts/linemark), [Swift Charts en iOS 16, WWDC 2022](https://developer.apple.com/videos/play/wwdc2022/10072/?time=510), [accesibilidad de Charts](https://developer.apple.com/design/human-interface-guidelines/charts). |
| **Flutter 3.50 + Dart** | Hot reload conserva estado para cambios Dart compatibles en desarrollo. Cambios a inicializadores, tipos incompatibles o código nativo pueden exigir hot restart o reinicio completo. Una sola UI sirve para ambas plataformas. Hay Widget Previewer como bucle adicional de componentes. | Material o Cupertino para formulario. `fl_chart` para la línea. `CustomPainter`, `Path.contains` y eventos de puntero para las zonas; añadir controles `Semantics` o semántica explícita al pintar. | **Alta** en widgets si se fijan SDK y dependencias. El agente puede verificar con analizador, tests de widgets y capturas; los errores del puente son otro ciclo. [Hot reload, actualizado el 29-09-2026](https://docs.flutter.dev/tools/hot-reload), [Widget Previewer](https://docs.flutter.dev/tools/widget-previewer), [Material](https://docs.flutter.dev/ui/design/material), [fl_chart](https://pub.dev/packages/fl_chart), [CustomPainter](https://api.flutter.dev/flutter/rendering/CustomPainter-class.html), [Path.contains](https://api.flutter.dev/flutter/dart-ui/Path/contains.html). |

**Hipótesis a probar.** Para la primera pantalla reutilizando el repo, Svelte tiene la ruta más corta a una vista nueva. Vue es la alternativa más cercana si el equipo valora un catálogo más integrado y herramientas de plantillas bien documentadas. Para editar sobre un móvil corriendo y conservar el estado del formulario, Flutter ofrece el mecanismo más directo de las rutas con UI nueva. Compose y SwiftUI pueden ser concisos por separado y tener el menor coste para ciertos controles de plataforma. Al evaluar los dos SO hay que sumar las dos implementaciones, incluyendo la geometría y las pruebas de cada una. Compose Multiplatform es una reserva razonable si el equipo prefiere Kotlin y una UI común. JetBrains declaró iOS estable en mayo de 2025 y documenta previews de código común. El informe anterior ya aborda los costes de su integración con Rust. [Flutter hot reload](https://docs.flutter.dev/tools/hot-reload), [JetBrains 1.8.0, mayo de 2025](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/), [tooling de Kotlin Multiplatform, mayo de 2025](https://blog.jetbrains.com/kotlin/2025/05/kotlin-multiplatform-tooling-now-in-intellij-idea-and-android-studio/), [comparación anterior](alternativas-tauri.md).

## Cómo hacer que Claude y Codex ahorren tiempo

El perfil de la tabla puntúa de manera cualitativa **qué puede consultarse y qué puede verificarse**. No hay mediciones de este proyecto para atribuir a ninguno de los modelos una tasa de acierto por framework. Vue, Svelte, Compose, SwiftUI y Flutter tienen guías que enlazan sintaxis, componentes, tooling y pruebas. Solid y Preact también tienen documentación utilizable, con más cuidado al mezclar ejemplos JSX. Dioxus y Slint ofrecen un punto de partida claro en Rust. En los toolkits experimentales, la referencia útil suele ser un ejemplo del mismo tag que cubra el backend exacto. Parte del coste aparece al corregir errores de API, no en la primera generación. [Guías de Anthropic sobre verificación](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips), [migración de Svelte](https://svelte.dev/docs/svelte/v5-migration-guide), [releases de Dioxus](https://github.com/dioxuslabs/dioxus/releases), [ediciones Slint](https://slint.dev/blog/slint-1.19-released).

- Darles el mismo paquete de entrada. Versiones bloqueadas, links de compilación y del API exactos, estados y tamaños de pantalla, geometría compartida, un ejemplo de formulario y el comando reproducible de verificación. Para Rust, pedir que reproduzcan el primer error y dejen un caso mínimo. E0277 señala un trait que falta y E0382 el uso de un valor que ya se movió. Resolver el origen evita que una sola causa genere una cadena de cambios en props, closures o callbacks. [Rust E0277](https://doc.rust-lang.org/error_codes/E0277.html), [Rust E0382](https://doc.rust-lang.org/error_codes/E0382.html).
- Dar acceso a un ciclo completo de comprobación. En web, chequeo de tipos y navegador con capturas. En Flutter, analizador, test de widget y emulador. En UI nativa, build y captura en el host que corresponda. En Rust, `cargo check` para diagnóstico y build real para enlace y empaque. Usar `cargo build --timings` para localizar recompilaciones y un cronómetro externo para medir cuándo se ve el cambio. Registrar las preguntas y correcciones humanas. [Cargo build](https://doc.rust-lang.org/cargo/commands/cargo-build.html), [Playwright](https://playwright.dev/docs/test-snapshots), [pruebas Flutter](https://docs.flutter.dev/testing/overview), [capturas Android](https://developer.android.com/training/testing/ui-tests/screenshot).
- Comparar al mismo agente, versión de modelo, nivel de esfuerzo, límites y permisos entre rutas. Si hay presupuesto para ambos agentes, ejecutar el mismo guion con Claude y con Codex en sesiones nuevas, alternar el orden y conservar los registros. Anotar si pasan el primer build, cuántas APIs incorrectas introducen, cuántos ciclos necesitan para verde y qué cambios manuales fueron imprescindibles. Evaluar visualmente contra los mismos criterios y conservar diffs para evitar que tamaño o LOC oculten trabajo humano.

## Orden de pruebas con una pantalla

**Control inicial.** Usar el TypeScript actual como referencia y medir cuánto cuesta reproducir o modificar ese flujo. Preparar un contrato pequeño y común para obtener historial y registrar un valor, con datos sintéticos fijos. Reutilizar las mismas zonas desde el mapa actual, el mismo texto y los mismos estados visuales. El caso contiene un campo de pulso en lpm y su error de entrada, guardado, línea con fechas, un punto o valor seleccionable, figura con el mismo conjunto acordado de zonas y alternativa mediante botones, y mensajes accesibles para selección, carga, error y guardado. Probar una serie corta de **30** puntos y otra de **2.000** como carga de ensayo propuesta. Mantener fijo el número de puntos realmente dibujados cuando se compare la fluidez. [Gráfica actual](../ui/src/ui/telemetry-history.ts), [mapa actual](../ui/src/ui/body-map.ts).

1. **Svelte 5 + Tauri.** Extraer sólo esta pantalla como componente del frontend existente. Reusar adaptadores, geometría y estilo donde resulte posible. Medir cuánto cuesta pasar del registro y sus estados a la gráfica y la selección del mapa. Comparar contra el control en navegador y en Android. Validar después la misma UI en iOS antes de generalizar el resultado a ambos SO. [Plantilla y configuración Tauri](https://v2.tauri.app/start/create-project/).
2. **Compose en Android y SwiftUI en iOS, con UniFFI.** Implementar la misma pantalla con datos de muestra en previews y en Android físico primero. Hacer una réplica iOS lo bastante temprano para sumar su coste, incluido el fallback de gráfica si se conserva iOS 15. Sustituir el mock por el mismo caso de uso Rust/SQLite una vez que la UI de ambos lados esté medida. [UniFFI](https://github.com/mozilla/uniffi-rs), [Previews Android](https://developer.android.com/develop/ui/compose/tooling/previews), [Previews iOS](https://developer.apple.com/documentation/swiftui/previews-in-xcode).
3. **Flutter con flutter_rust_bridge.** Hacer una única vista con widgets y hot reload, medirla primero con el mock y después enlazar el caso de uso. Ejecutar el flujo en Android e iOS antes de comparar el total con la pareja nativa. Si se fija que la UI debe escribirse en Rust con renderer propio, usar este cupo para Slint y exigir que las zonas, el campo de texto y las capturas funcionen en los dos SO. [Flutter hot reload](https://docs.flutter.dev/tools/hot-reload), [flutter_rust_bridge](https://cjycode.com/flutter_rust_bridge/), [Slint móvil](https://docs.slint.dev/latest/docs/slint/guide/platforms/mobile/general/).

Para cada ruta separar **A** (UI con mock y primera ejecución en cada plataforma) de **B** (flujo real, persistido por el mismo núcleo, reabierto sin red). Así se ve si el ahorro se produce al maquetar, al corregir, al tender el puente o al reutilizar. Usar un Mac comparable para las ejecuciones iOS y registrar si fue necesario alternar de equipo. El informe anterior contiene el guion de compatibilidad móvil más amplio. [Informe anterior](alternativas-tauri.md).

**Regla de decisión propuesta.** Primero pasar la misma aceptación funcional y de accesibilidad y comprobar la fluidez en físico. Entre las rutas que la pasen, elegir por menor tiempo total hasta el flujo verificado en los dos SO y menor tiempo de corrección ante cambios. Usar LOC y tamaño para explicar diferencias y decidir empates. Si Svelte gana el bucle de edición y la WebView supera la prueba en los dispositivos objetivo, usarlo para pantallas nuevas o aquellas donde reduzca mantenimiento. Si una UI compartida sigue siendo prioritaria y Flutter gana en móvil de extremo a extremo, ampliar Flutter. Si la pareja nativa ofrece un resultado significativamente mejor en interacción o accesibilidad y el coste medido de sostener dos UIs es aceptable, seguir con Compose y SwiftUI.

## Qué no pude verificar

- **Tiempos, líneas y binarios de Pulsys.** No hay en esta revisión tiempos de build/frío/HMR medidos en el equipo, LOC de la pantalla equivalente, APK/IPA comparables, fluidez en físico, memoria o batería. Las fichas y demos de los proveedores sirven para diseñar la prueba.
- **Calidad real de Claude frente a Codex por framework.** No encontré una comparación pública que controle modelos, versiones, permisos y esta combinación de formulario, gráfica, SVG/Canvas y entrega móvil. El perfil por opción es una inferencia de documentación, estabilidad y capacidad de verificación. Tampoco se hizo un conteo sistemático de ejemplos.
- **Cobertura de los renderers Rust.** Quedaron sin verificar TalkBack, VoiceOver, IME, focos y recarga en los backends móviles concretos de Dioxus Native, Slint, Iced, eframe, Makepad, Xilem, Freya, GPUI y Floem según corresponda. También queda sin verificar el trazado, clip y selección exacta de la figura actual en esos backends. El soporte o la ausencia de evidencia se indica por fila.
- **Compatibilidad de las combinaciones exactas.** Quedan pendientes dependencias de gráficas/componentes con las versiones elegidas, disponibilidad de todos los controles en los OS mínimos, paridad entre preview y teléfono y calidad de la exportación de diseño sobre la pantalla real. El fallback de Swift Charts para iOS 15 es una propuesta de implementación.
